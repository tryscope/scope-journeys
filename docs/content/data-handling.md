# Data handling

*Written so it can be handed to a customer's security review as it stands. It contains nothing a customer who installs the sensor cannot already see.*

**What it is.** Scope Journeys is a small observer that runs inside your own stack, in front of your documentation host and your API and MCP host: a Worker in your Cloudflare account, one condition in the proxy file of your Next application, a mount in your Express, Fastify or Hono app (or the standalone proxy in front of an origin you do not run), or an external processor beside the Envoy or Istio you already run. It forwards every request to your origin unchanged in substance and reports a hashed summary of the request and the answer to Scope, so that Scope can show you how coding agents (Claude Code, Codex, Cursor) find, install, sign in to and use your product, and with what intent. A connector (a Vercel log drain, a Cloudflare Logpush job) delivers your platform's own request log instead, for a first day with nothing deployed.

**Where it runs.** In your infrastructure only. Scope runs nothing in your request path: no DNS record points at Scope, no certificate for your hostname is issued elsewhere, and TLS is terminated where it is terminated today. The observer is the package you installed, readable in `node_modules`; the configuration it runs under is a public document you can read in the console.

**What leaves your infrastructure.** For each request, one record: method, host, path and query string, status, timing, the client's user agent, Accept and fetch-metadata headers, the network facts your platform exposes (AS number, country, TLS version, JA4), a one-way hash of the client's address, a one-way hash of any credential (bearer token, device code, install id) and of the MCP session id, the reference code if one was carried, the outcome of a Web Bot Auth signature check (the signer, its key id and the reason), the MCP method, tool and client names and the OAuth grant type, client name, resource and scope a call names, the intent an agent declares (redacted like a body), and what the observer did. In the query string and the `Location` header, the value of a parameter named `api_key`, `key`, `token`, `access_token`, `refresh_token`, `id_token`, `code`, `client_secret`, `password`, `secret`, `signature`, `sig`, in any case or spelling (`apiKey`, `api-key`, percent-encoded or inside a URL carried by another parameter), leaves only as a one-way hash, whatever your policy says; a valid reference code stays readable only in the parameters your policy says carry one, and a string holding more than 64 such values leaves as one hash. Only when your policy turns `record_bodies` on and lists fields in `observe.bodies.allow_fields`, and then only on the routes your surface map observes (the answer's body also on an error answer, status 400 or above, from any route it does not pass through) and only up to 64 KB, the request and response bodies, cut to the fields you allow, with the values of your secret fields and of the secret names above, and your secret value shapes, hashed wherever they appear; in the lightest form, the default, no body at all. The records travel to Scope's ingest over HTTPS after the response went out, one call per request, authenticated by your install key or, on Vercel, your project's OIDC identity. A connector's log line becomes the same record on Scope's side, the client's address hashed before it is stored.

**What never leaves.** A raw client address. A raw credential: the bearer, the API key, the device code and the install id leave only as one-way hashes, salted per installation with a salt `init` generated on your machine and Scope never receives. Cookies, the `Authorization` value and `Set-Cookie`. A text or HTML body: a documentation page is recorded as its path, its face and its size, never its text. The content of an event stream: only its size. A body on a route your surface map does not observe (an error answer aside), or a body field `observe.bodies.allow_fields` does not list, beyond the MCP and OAuth facts and the declared intent above. Anything at all from an observer without its salt. The key the observer signs its assertion with. Your origin's answer beyond the facts above.

**What it adds to your traffic.** On every request it forwards to your origin it adds a `Via` header naming itself, and it removes hop-by-hop headers and the client's `accept-encoding` and `content-length` as a conforming gateway does. Beside fetching its policy from Scope and shipping records to it, its one request of its own is the key directory of a signer the policy's `signers` list names (by default Exa's crawler and ChatGPT), fetched to verify a Web Bot Auth signature and cached for an hour; a signature from any other signer is recorded and causes no request. Where your traffic, records and install key go comes only from your own configuration, never from the policy; nothing ships without your install's key or, on Vercel, your project's OIDC identity. The policy cannot name a credential-carrying header such as `Authorization` or `Cookie` for recording, may add only its own `x-` headers on the hop, and the text a rule adds holds only plain text, its codes, a short list of tags and links to your own site. Nothing else changes until you turn a rule live in the console: every rule is dry run when you install it, computing what it would do, recording it and changing nothing on the wire. A live rule applies only where your surface map names: `inject` and `notfound` on the documentation paths the map lists, `finder` and `gate` on their exact routes, `error` on its route pattern; a path the map does not name is never changed by any rule, whoever the reader is. A live rule may: add a short reference code (`?ref=...`) to the links, the install command and the MCP URL on a mapped documentation page, and a setup and intent header line to the API samples on that page; list a tool named `declare_intent` first in your MCP server's tool list, which it answers itself with a fixed acknowledgement and never forwards to your server; answer the documentation-finder route (`/api/docs/find`) itself with links to your guides; answer a mapped documentation path your origin does not have with a page listing your real guides (the status stays 404); append "Guide: <link>" to your API's own error messages for the statuses you choose. Nothing else in any response is changed. Every change is served to people and agents alike, there is no agent-only answer, and each one is visible to the agent, the person using it, and to you in the console.

**What it holds.** No secret of yours: the observer's own credential is an installation key you can rotate or revoke at any time, or, on Vercel, your project's OIDC identity with no key at all. Its configuration is a public document with no secret in it, signed by Scope and checked before use. It stores nothing on your infrastructure.

**How it fails.** Open: if the observer cannot reach Scope, cannot load its configuration, or encounters an error, your request is forwarded unchanged and your origin's answer is returned as it was. Once a request may have reached your origin it is not sent again: when its forward fails after the request left (the connection drops, or no answer within 30 seconds), the client gets a 502, or a 504 on the timeout. The one exception is HTTP's own: on the Node form, a GET, HEAD, OPTIONS, PUT or DELETE whose kept-alive connection was reset before any answer goes once more on a fresh connection. With no configuration it runs its built-in default, which changes nothing on the wire, and each record it makes says so. Without its salt it forwards every request untouched and sends nothing, and `journeys doctor` names the missing salt. It never retries a report more than once and never delays a response to report.

**Where the data goes and for how long.** To Scope's ingest over HTTPS after the response went out, one call per request; stored in your tenant for 90 days by default, with the raw batches kept append-only as the audit trail; exportable to your own OpenTelemetry collector as log records and traces; deletable with your tenant.

**How to remove it.** Delete the Worker, the condition, the mount or the filter (`journeys uninstall` reverses every write `init` made); your product is as it was. Your data remains yours to export or delete.

**What it is not.** It is not a firewall, it blocks nothing; it is not an identity provider, it issues no credential and sits in no sign-in; it does not read transcripts; it does not host your MCP server.

The field-by-field list is [Telemetry](/telemetry), generated from the record schema the packages ship; the provenance of every release and the vulnerability address are in [Security](/security).
